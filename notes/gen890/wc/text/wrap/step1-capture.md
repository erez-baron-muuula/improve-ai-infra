Reference file for the `/wrap` runbook (`C:/Users/Erez/.claude/skills/wrap/SKILL.md`), which sends you here at Step 1. The runbook keeps every step's order and its non-negotiables; this file holds the full detail, moved here word for word (a pointer to text now in another file names that file).

## Step 1 — Capture unresolved items (all sessions)
Auto-file every unresolved item this session surfaced as its own Notion Team-Tasks ticket, for future discussion. Do NOT ask Erez to weigh in on, approve, or apply any of them during the wrap — file silently; the Step 7 report's past-tense list of what was filed is required and is not "discussing" them. This step runs in every session (it is not project-gated; a global-only session still runs it — it is not one of the project-specific steps Step 0 skips). It **overrides, for capture-only filing, for the on-demand ref-file appends in sub-step (3), and for the weekly size check's ticket filing and raising (config-health `size-weekly.md`),** the standing rules "Before creating or materially changing a ticket in a tracker, draft the full proposal" and "On \"apply learnings\"" (their approval-before-filing gates) — it does **not** override approval for applying a learning to any other home (`CLAUDE.md`, a skill, a hook's code; those still need `/check` + Erez's approval in a future session), and it does not change the assignee logic in sub-step 7.

**Every Team-Tasks write this step and Step 3c make goes through the ticket-quality gate (GEN-508), UNATTENDED (GEN-702).** The gate hard-blocks every Team-Tasks create / duplicate / move / substantive-body edit unless a single-use pass minted by an independent review exists, so each write here — the create in sub-step 7 (and, if the GEN-145 symptom appears, its in-place body repair), the near-duplicate body append in sub-step 6, and Step 3c's create and append — is filed by running the `/vet-ticket` machinery: **reference that skill's flow, do not re-specify it here.** Per item, run it unattended: draft the payload — set `Urgency`/`Gain ratio`/`Priority` per `/vet-ticket` Step 1, which treats a create and a material body append alike (both are material, so both derive these fields) → get its `contentHash` per `/vet-ticket` Step 1 → spawn ONE independent `check-reviewer` against the ticket bar (`/vet-ticket` Step 2) → resolve any notes, then write the ticket-record (`/vet-ticket` Steps 3–4), with `source` set to `wrap-step1` for this step's writes and `wrap-step3c` for Step 3c's → run the `/vet-ticket` Step 7 evidence precondition → mint the single-use ticket pass → issue the Notion write → re-fetch and confirm it landed (`/vet-ticket` Step 8). **No Erez-facing card:** Steps 1 and 3c, and the weekly size check (which uses `source` `wrap-step1`), carry the standing override exempting them from the draft-for-approval pause, so `/vet-ticket` Step 5's card is skipped and the mint proceeds silently; the Step 6 waive lane needs Erez and is therefore unavailable here. `check-reviewer` has no Notion tool, so the near-duplicate search is NOT its job on this lane — sub-steps 5–6 already did it before drafting; the reviewer judges only ticket quality against its bar.

**Bounded — an unattended filing must never loop or hang the wrap.** If the reviewer does not return a clean PASS, amend the drafted payload per its findings and re-review with a fresh `check-reviewer` (re-hashing first) — but cap this at **2 further review rounds** (count every round that does not end in a clean PASS, not only literal REVISE verdicts). If the cap is reached, OR the item is blocked on information only Erez holds, OR any step of the machinery hard-errors (a non-zero `--ticket-hash` exit, a mint or evidence-precondition failure, a post-mint apply failure such as `consume-failed` or a Notion API error, a sidecar/transcript read failure — illustrative, not exhaustive: any hard error stops it) → do NOT force-file and do NOT loop. Leave the item unfiled, surface it in the Step 7 report **with enough substance to act on later**, and record it durably so a gate-blocked capture is not lost — in the Step 4 HISTORY.md entry (per Step 4 sub-step 2) when this wrap logs a project, or, when the wrap logs no project so Step 4 is skipped (Step 0), in a dated recovery file `C:\Users\Erez\.claude\wrap-surfaced-not-filed-<timestamp>.md` whose path the Step 7 report then names (Step 1 runs in every session, so its durability is unconditional too) — for a later manual `/vet-ticket`. Once a recovery file's items have all been filed, rename it to `wrap-surfaced-filed-<same timestamp>.md` rather than deleting it; Step 3i reports recovery files not yet renamed. **A surfaced-not-filed item counts as a note the steps require surfacing**, so it forces the full Step 7 report (never the all-clean fast-path). (Same posture as sub-step 7's GEN-145 handling: once, do not loop.)

**Report what was filed and how the reviews went (interim early-warning — GEN-702).** For EACH item this step filed, the Step 7 report shows its reviewer outcome inline (e.g. `reviewer PASS, N review round(s)`), plus a one-line per-run tally: count filed; count that needed more than one review round before PASS; count surfaced-not-filed (per the bound above). Step 3c reports its own single filing the same way, in its own report line (Step 3c, in `readouts-3b-3c.md`). This is computed from this run's own observation of the filings it just made. It is the per-run, after-the-fact visibility signal on this unattended lane, **not** a cross-session aggregate. Step 3i's readout is the cross-session view, but it leaves this lane's filings (tagged by `source`) out of its re-review rate, so leniency confined to this lane is visible only in this per-run tally. (`waived`/`declined` cannot occur on this lane — there is no card — so they are not counted.)

1. **Decide what's already resolved** (so it isn't re-filed): from the session itself, an item is resolved if you already applied it (a rule/skill/hook/file edit you made this session), already filed it as a ticket this session, or already resolved it with no open thread remaining. Judge this from the session — do not reconstruct it from the auto-approval log or git history. **After a `/compact`, the in-context summary is lossy and may omit what was applied or filed — source this from the on-disk transcript, not the compacted summary** (same as Step 4). The dedupe query in (5) is the durable backstop against re-filing something a *prior* session already captured.
2. **Identify unresolved items** — anything worth keeping that surfaced this session, is NOT resolved per (1), was NOT explicitly rejected by Erez, and is not a solution/feature/approach you VOLUNTEERED UNPROMPTED that Erez then didn't take up (he met it with silence or a topic change — a lapsed unprompted offer isn't an item he's carrying; this does NOT apply to a recommendation he ASKED you for, nor to anything he ENGAGED with, e.g. asked about or said "maybe later" — those stay fileable as deferred decisions/open questions; and when you genuinely can't tell whether his silence meant a lapse or a still-open thread, file it, per this step's default of never dropping on an uncertain call): behavioral learnings (candidate rule/skill/hook), technical findings / tech debt / bugs, follow-up action items, deferred decisions / open questions. **Among behavioral learnings, treat as a candidate every reversal Erez's pushback caused this session — everything GEN-58 (a) already flagged live, plus any his pushback caused that it didn't catch, whether he challenged a position and you reversed it or asked a probing question whose honest answer exposed a problem you should have caught in your own `/suggest`/`/check` pass before presenting (mere elaboration, or a question that adds genuinely new scope rather than testing what you already gave, does not count). Post-`/compact`, source these from the on-disk transcript per (1). For each, judge whether the flip reveals something about how you reason or work — deferring to his tone over a real argument, missing something self-review should have caught, or under-delivering a quality pass you implied was done. If it does, file it via (3)'s triage like any other behavioral learning. If not — the flip merely absorbed genuinely new information he supplied, or the gap a question exposed was minor, case-specific, and not a repeatable habit — do not file it, but record it in one line in the HISTORY.md entry ('Reversals judged non-learning: …') so the negative judgments stay reviewable. This is independent of GEN-58's immediate in-session log; a reversal may qualify for both.** **File generously:** include it unless it was already captured in a ticket this session, already resolved-and-closed with no open thread, or Erez rejected it. This excludes only the volunteered offer's content; a genuine behavioral learning the episode revealed (e.g. that you volunteer unrequested work) is still captured via (3). If none, this step is silent.
3. **Triage each behavioral learning by trigger before filing.** (Non-learning items — technical findings, bugs, follow-up actions, deferred decisions — skip this and continue to (4).) Decide its route:
   - **On-demand gotcha, trigger already wired** — a situational gotcha or judgment heuristic whose triggering context matches an existing injection ref (a `hooks/refs/<topic>.md` delivered by a registered hook — check `C:\Users\Erez\.claude\hooks\refs\`) → append it to that ref file now, matching the file's format; keep it to 1–3 lines and prefer merging into an existing bullet over adding a new one; a project-specific gotcha names its project inline. The Notion and shell notes are split across several files: pick the one whose description in the "Other Notion notes" / "Other shell notes" list at the end of `notion.md` / `shell.md` fits, use `notion.md` or `shell.md` itself only when none does, and add a new bullet after the last bullet of the file's opening bullet list, before any `##` heading. **Then measure the file** (`Get-Content -Raw -Encoding UTF8 '<path>' | Measure-Object -Character` in PowerShell): if it is now **over 9,000 characters**, flag it in the Step 7 report's "📌 For you" block, naming its split ticket — the file is near the 10,000-character limit above which Claude Code shows sessions only a 2,000-character preview of an injected note, so it needs splitting; the flag counts as "a note the steps require surfacing," forcing the full Step 7 report rather than the all-clean fast-path. The split ticket is titled `Keep refs/<file> under the injection limit`: if one is already open (dedupe by exact title per (5)), leave it as is; otherwise file it through the unattended gate flow above, under the AI-infra epic, its body naming the file, its size, the 10,000-character limit, and GEN-825 as the record of how the Notion and shell notes were split. File NO ticket for the gotcha itself. Quote every append or merge verbatim (before/after for a merge) in the Step 7 report.
   - **Enforceable candidate** — could become a rule, a skill, a hook, or other system enforcement → continue to (4) and file a ticket as usual (applying it later still needs `/check` + Erez's approval). If it ALSO matches a wired trigger, do both: the ref-file append above for immediate coverage, plus the ticket — noting in the ticket that the append already covers the gotcha, so the future apply session builds only the enforcement.
   - **Triggerable topic, but no injection hook exists for it yet** → append it to that topic's single accumulator ticket titled 'Build injection ref: <topic>' where <topic> is the intended ref filename, lowercase (e.g. 'browser') — create it under the AI-infra epic if absent; dedupe by exact title per (5). Never build or register the hook during /wrap (locked-config change). Each wrap, Step 7 flags every open accumulator ticket currently holding 3+ learnings as ready to build (re-checked via one title-prefix query each run — not only when newly crossed).
   - **No reliable trigger, and it doesn't clear the always-loaded-rule bar on its own merits** → DROP it: record it in one line in the HISTORY.md entry ('Dropped learnings: …') and file nothing.
   - **Unsure which branch applies** — if none of the above confidently apply → continue to (4) and file a ticket as today, noting the open classification question in its body, for joint classification in a later session. Never drop — and never append to a ref file — on an uncertain call.
   If the session surfaced no learnings, the triage writes nothing and reports nothing — the step gets only its checkmark in the roll-up, like any other clean step.
4. **Triage each to a parent.** Route by domain per the global rule "Route a ticket by the domain the problem belongs to, not by who fixes it" (a learning genuinely about Claude's own behavior/workflow → the AI-infra epic even during a project session; a project/tool-specific item → that project's epic). Epic IDs come from the global `CLAUDE.md` Projects Directory table, read at wrap time. If the session ties the item to a specific existing ticket beyond doubt (worked this session, or its ID named), parent it to that ticket as a sub-item; otherwise parent it to the domain epic. When in doubt, use the epic — never guess a ticket parent.
5. **Dedupe before creating.** Query the Team-Tasks database for an existing open ticket with the same title under the chosen parent, via the Notion REST API exact-title filter (`POST /v1/databases/<id>/query`, `title`/`equals`) — NOT `notion-search` (semantic; cannot match by title). If found, skip and leave it untouched — never overwrite its properties.
6. **Check for an existing home before creating (semantic near-duplicate).** Ticket-bound items only — skip the two routes in "Triage each behavioral learning by trigger" that don't create a fresh ticket (the ref-file append and the "Build injection ref" accumulator ticket, which already have their own merge targets). Sub-step 5 catches only an identically-titled ticket; this catches a differently-worded **open** ticket about the *same underlying issue*, so the board doesn't accumulate near-duplicates. Query `notion-search` for the learning's underlying issue — its behavior and root cause, not its verbatim title (`notion-search` is semantic, so it surfaces reworded matches an exact-title filter cannot). `notion-search` cannot filter by status, so **discard from its results any ticket whose Status is not open (drop Done/Review/closed), and any ticket filed earlier in this same wrap run** (the IDs sub-step 8 tracks), before judging a match. Among what remains, a match is **confident** only when an open ticket is about the same behavior and same root cause, such that a future session working that ticket would naturally also resolve this learning; a same-area-but-distinct failure is NOT confident. On a confident match → do NOT create a new ticket: append this session's addition to that ticket's body under a dated `Also surfaced (YYYY-MM-DD):` line (leaving the original body intact) — filing that body append **through the unattended gate flow above, as an `update`** — and record it for the Step 7 report as `Merged into <ID>` (with its reviewer outcome). On anything less than confident → create the ticket per the following sub-step, per the standing "never guess on an uncertain call" posture ("Unsure which branch applies" in "Triage each behavioral learning by trigger", and "never guess a ticket parent" in "Triage each to a parent"). Post-`/compact`, source the learning's own text from the on-disk transcript per (1).
7. **Create one ticket per item — through the unattended gate flow above, as a `create`** — status per the global rule "When creating a ticket, the status you set or propose is the one actually true of it" (a captured item a future session can just pick up is **To Do**; one filed under "Unsure which branch applies", needing joint classification with Erez, is **Blocked**; use Backlog only when it genuinely waits on something else first); type task; parent per (4); Task template applied (check the template exists and apply it, per `/vet-ticket` Step 1). Assignee: **unassigned**, EXCEPT an item the session establishes as needing a step only Erez can physically perform (manual UI inspection, real-world action, or a sign-off Claude cannot self-serve) → assign to Erez; anything Claude could do in a future session stays unassigned. Body is **self-contained** (what was observed; for a behavioral item, why it may be a rule/skill/hook; the relevant session detail) — no link back to HISTORY. After creating, re-fetch and verify the body + key properties landed (per the standing post-create verify rule); ONLY IF the GEN-145 symptom shows (blank or duplicated heading), repair that one ticket's body in place — write the corrected body onto the already-created page through the unattended gate flow above, as an `update` and as a full-content body replace (not a targeted find/replace, so the malformed heading is fully cleared; and not a second `create`, which would leave a duplicate that sub-step 5's dedupe then protects) — once, do not loop.
8. **Carry the filed ticket IDs (in this run's working memory) to Step 4 and Step 7.** A hard failure mid-step may leave some filed but un-reported; the dedupe in (5) prevents a re-run from double-filing, and they surface next wrap.
