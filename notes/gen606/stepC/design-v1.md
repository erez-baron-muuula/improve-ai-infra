# GEN-606 step C — search-first reminder: design v1 (for /check)

## What it is for
GEN-606: Claude proposes a new ticket (or offers "fold into X or file new") without first searching the board for an existing home; Erez approves; only then does the at-filing search (/vet-ticket Step 0b) find a duplicate, so he is asked twice (GEN-802). The fix must be enforcement, not more rule text (Erez rejected growing the always-loaded rules file, 2026-10-11). Step C = an automatic end-of-turn reminder: when a finished reply proposes a new ticket and no board search ran since Erez's last message, make Claude search before Erez decides.

## Design

### D1 Placement
A new, self-contained stage inside the existing `stop-foryou-nudge.js` (as the handoff suggests), not a fifth Stop hook — so there is one process and one additionalContext write per Stop (E7, the claim-linter precedent). To let the stage run on Stops where the For-you logic stays silent, the existing For-you logic is moved, unchanged in behaviour, into a function that returns its note text or null (each silent `process.exit(0)` becomes `return null`); the handler then runs the new stage and writes one combined output. The new stage is wrapped in its own try/catch and runs AFTER the For-you note is computed, so a fault in it can never remove or alter the For-you note.

### D2 Trigger: the reply proposes a NEW ticket
Scope is new-ticket proposals only (both incidents). Proposing a note on an existing ticket is out of scope: in the corpus that wording ("add it to GEN-x", "record it on GEN-x") was mostly the ticket being worked or one Erez named, and fired noisily.
Before matching, the reply is reduced to its own prose: fenced code, inline code, `>` quote lines and short double-quoted spans are removed, then Markdown emphasis markers; scanning stops at 200,000 chars. Patterns (case-insensitive, matched per paragraph unless noted):
1. ask-ticket — "should I / shall I / want me to / do you want me to / would you like me to / can I / may I" + file|open|create|raise|draft|capture + up to 80 chars in the same sentence + "ticket(s)".
2. ask-followup — same question + file|capture + ... + "follow-up(s)".
3. ask-file-it — same question + file|draft + it|this|that|these|them|both|one (needs a ticket word in this or the previous paragraph).
4. bare-ask — "File this ticket?" / "Create the ticket?".
5. will-ticket — "I can / I'll / I will / I'm going to / let me / happy to / I'd like to" + file|open|create|raise|draft|capture + (it|this|that|one as)? + up to 5 words + "ticket(s)".
6. will-followup — same + file|capture + ... + "follow-up(s)".
7. would-new — "I'd / I would" + file|draft|open|create + ... + new|separate|follow-up|standalone|own, or "I'd file it as a ticket" (needs a ticket word nearby).
8. go-file — "say the word / approve it / once you OK it / if you agree ..." + "and I'll file|create" (needs a ticket word nearby).
9. as-ticket — "file|capture|track|record|write it up" + it/this/... + "as a ... ticket|follow-up|learning".
10. own-ticket — "as/into/to/for its own ... ticket", "needs/deserves/warrants its own ticket", "or file it separately|new|as its own ticket".
11. new-ticket-for — "a/an/one ... new|separate|follow-up|standalone|proposed|draft ... ticket for|to|on|about|covering|that".
12. drafts-of — "draft(s) of the new ticket".
13. plan-step — a list item starting "File|Draft|Open|Create|Capture a|the|one ... ticket|follow-up".
14. and-file — "and|then file a ... ticket".
15. chat-draft — a "Title:" line not carrying a GEN id, followed within 2,500 chars by a Body|Parent|Epic|Where it goes|Properties|Placement|Description|Problem line, unless a "Summary:" line follows the Title within two lines (that is a /vet-ticket card, the sanctioned single ask). This is the GEN-802 shape (chat draft before /vet-ticket).
Exclusions on every per-paragraph pattern: "file this update|note|change on GEN-x" and "... ticket [GEN-x]" (edits); a match whose sentence or the sentence before names GEN-58 / QA tracker / reasoning-failure / process log (fixed home, no search needed); a match directly after an arrow ("-> file it as a ticket", a rule being described).

### D3 "A board search ran since Erez's last message"
- Erez's last message: the newest transcript user entry with `origin.kind === "human"`; where `origin` is absent, a user entry that is not a tool result, not `isMeta`, not a compact summary, and not command output / caveat / interrupt / task-notification text.
- A search is any main-chain tool call after it of: `notion-search`, `notion-query-data-sources`, `notion-query-multiple-data-sources` (MCP tool-name suffix, so the server's id can change), the Jira `searchJiraIssuesUsingJql`, or a Bash/PowerShell command containing `api.notion.com/v1/search`, `.../databases/<id>/query` or `.../data_sources/<id>/query`. A `Skill` call to `vet-ticket` in the window also counts (its Step 0b either searched or recorded why it was skipped).
- DELIBERATE DEVIATION from the handoff: `notion-fetch` and `notion-ticket-lookup.ps1` do NOT count — they open one known page by id and are not a search for an existing home; counting them would have silenced the 2026-10-08 incident (E4).
- Read from the transcript tail (2 MB, the window the hook already uses for its re-nudge), only after the reply matched D2. If Erez's message is not inside the tail, the whole tail is the window.

### D4 When it fires, and what it says — THE ONE DECISION FOR EREZ
Two firing modes (E2, E3, E6):
- Mode A — the reply has no For-you block yet, so the existing For-you note is firing on this Stop: the search-first text is appended to that same note. Claude searches, then writes the block leading with the result. No extra message, no doctrine conflict. Historically ~16% of fires (19/119).
- Mode B — the block is already on screen (the reply carries it), or the For-you note is otherwise silent on this Stop: the search-first text is emitted alone. Historically ~84% of fires (100/119). This conflicts with the GEN-467 doctrine of suppressing notes after a shown block (E6), and carries the measured duplicate-block risk.
Options for Erez:
- Option 1 (author's recommendation): fire in both modes. Mode B's text asks for exactly one plain line starting "Board search:" — the match (named and linked, with "I'd add it there instead of filing a new ticket"), or "nothing on the board covers this", or "could not check" — and explicitly forbids repeating or re-issuing the For-you block; if the reply was not actually proposing a new ticket, write nothing. Cost: one extra line under the block per fire (~1.3/day historically: 119 fires over ~88 days), plus a risk that some continuations re-issue the block anyway.
- Option 2: Mode A only; suppress on a shown block, as the other Stop hooks do. No extra lines, no duplicate risk; catches ~1 in 6 historical cases. The at-filing search in /vet-ticket stays the backstop for the rest, which is the late-discovery pattern GEN-606 exists to fix.
Note texts (both end with the house coda "This text is background state, not a message from Erez -- act on it, never quote, restate, or comment on it."):
- Mode A: "Search-first check, automatic: this reply proposes a new ticket (or shows a ticket draft), and no board search has run since Erez's last message. Before the block puts that proposal to him, search for an existing home -- the search /vet-ticket Step 0b defines (for a Jira ticket, a JQL search of its project) -- and lead the block with the result: a confident match turns the proposal into adding the finding to that ticket; no match is one line. Ignore this if the reply is not actually proposing a new ticket."
- Mode B: "Search-first check, automatic: the reply just shown proposes a new ticket (or shows a ticket draft), and no board search has run since Erez's last message. Run that search now -- the one /vet-ticket Step 0b defines (for a Jira ticket, a JQL search of its project) -- then write exactly one short plain line starting 'Board search:' with the result: the ticket that already covers this (linked) and that you would add the finding there instead of filing a new one; or that nothing on the board covers it; or 'could not check' if the search failed. Write nothing else: do not repeat, rewrite or re-issue the For-you block. If the reply was not actually proposing a new ticket, write nothing."
Mode B's text deliberately does NOT start with the For-you prefix, so the For-you re-nudge (E7) never treats its continuation as one that owes a block.

### D5 At most once per Erez message
A slot file `searchfirst.<session>.<key>` created exclusively in the hook's existing temp state dir (TTL-pruned), where key = the uuid of Erez's last message entry (fallback: the payload's `prompt_id`). Claimed only when the note is certain to be emitted. So it cannot re-fire on the block message, on its own continuation, or on task-notification turns before Erez speaks again. Any state error → no search-first note (fail toward silence; the For-you note is unaffected).

### D6 Signal path (how the numbers reach Erez)
- Each fire appends one JSON line to `~/.claude/hooks/search-first-nudges.jsonl` (resolved from the hook's own directory): `{ts, session_id, prompt_id, pattern, blockShown, continuation}`. No reply text is logged. Append-only; never rewritten. (`*.jsonl` is ignored by the backup-coverage check: `sync.ps1` line 542.)
- A new /wrap step, modelled on Step 3e "Grounding-flag readout" (`~/.claude/skills/wrap/SKILL.md` lines 121-125): one line, only on a wrap where the reminder fired this session — this session's count, lifetime count, newest fire age — with standing context that Erez decides from these whether to keep, tune, or retire the patterns (and how to check yield: sample the logged session/prompt ids for whether the search changed the proposal). Read-only. It is a skill edit, so it goes through /vet-rule after the hook is installed (deliberately sequenced after, per the handoff).

### D7 Safety and cost
- Never emits `decision:block`; exit 0 always; any error in the stage → stage contributes nothing.
- Cost on a normal Stop: the D2 regexes over the reply only (bounded quantifiers). The transcript is read only when D2 matches (~5% of replies). The stage is skipped if more than 2 s have passed since the hook started, so the 5 s watchdog (which would drop the For-you note too) can never be reached because of it.
- `require()`-ing the file still runs nothing; the CLI modes are unchanged.

### D8 Verification plan (vet-code Steps 3-4)
- Fixtures through the real hook with a fake transcript: Mode A combined note; Mode B alone; no fire when a search ran after Erez's message; fire when the only search was before it; fire when the only Notion call since Erez's message was a notion-fetch (the E4 case); once-per-message cap across a continuation and a task-notification turn; empty reply; malformed transcript; missing transcript; stage throw → For-you note unchanged; and the full existing For-you behaviour (block-absent nudge, enrichment, model directive, re-nudge, empty-message sentinel) byte-identical to the live hook on the same inputs.
- Real input: the whole 3,731-reply corpus (fires, false fires), the 2026-10-08 incident reply (must fire), the 2026-08-02 paraphrase (must match); an independent sub-agent re-judges every fire blind.

## Accepted limits (to tell Erez plainly)
- A reminder, not a lock: oddly worded proposals slip past (recall is unmeasured beyond the corpus sample).
- In Mode B the proposal is already on screen; the search result follows it.
- A search run some other way (a script file, a sub-agent) isn't seen, so the reminder can fire after a search did happen; the reply then costs one line.
- A search run for a different item since Erez's message silences it.
