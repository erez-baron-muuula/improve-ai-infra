# Design: plan-mode prompt answerer for 5 allow-listed read-only tools (GEN-952, attempt 2) — round 2

## Problem (provenance)
- 5 tools are bare entries in ~/.claude/settings.json permissions.allow (parsed this session; reviewer cites lines 66, 73, 77, 80, 90): mcp__scheduled-tasks__list_scheduled_tasks, mcp__scheduled-tasks__list_task_runs, mcp__ccd_session_mgmt__list_events, mcp__ccd_settings__get_settings, mcp__claude-in-chrome__tabs_context_mcp.
- In plan mode they still prompt Erez: 10 prompts in 14 days, 0 outside plan mode (count-planmode-prompts.js output this session: list_events plan 1/1, get_settings plan 1/1, tabs_context_mcp plan 12/3, list_scheduled_tasks plan 6/3, list_task_runs plan 2/2; all other modes 0 asked). Caveat: the script labels a call with the last permissionMode seen, so some "plan" denominators include calls just after a plan approval; the prompt counts are the meaningful figure. One prompt record carries the explicit reason: Improving PC Processes transcript e69d4646 line 218, 2026-10-26T09:35:52Z, list_scheduled_tasks: {"decision":"accept","source":"user_temporary","grantScope":"once","reasonCode":"mode:plan"}.
- Comparator: get_session (allow-listed, not in auto-approve's SAFE_TOOLS) 5 plan calls / 0 asked; mark_chapter 15/0 (same script, this session).
- Cause, confirmed by a Claude Code maintainer (bcherny) on anthropics/claude-code issue 76238 (fetched this session, closed as not planned): "Since roughly v2.1.204, plan mode treats any MCP tool that isn't marked read-only (via the MCP readOnlyHint annotation) as a potential write and always prompts for it, even when an allow rule matches". Erez cannot add that marking to these vendor-built tools.
- Attempt 1 (an explicit PreToolUse "allow" in auto-approve.js) was dropped before install: permissions doc "Hook approvals in plan mode" (local copy docs/permissions.md line 657): "In plan mode, apart from ExitPlanMode, your PreToolUse hook's "allow" has no effect on a file edit or another call that isn't read-only." Changelog ~/.claude/cache/changelog.md line 337 (2.1.299): "Fixed plan mode running a write (an MCP tool's, a file's, a shell command's) that a PreToolUse hook or a mod's tool.check hook allowed". Installed version 2.1.308 (session transcript line 3).

## Evidence for the proposed mechanism
Vendor docs (raw copies downloaded this session to scratchpad/docs/):
- hooks.md 2074: PermissionRequest "Runs when Claude Code is about to ask you for permission to use a tool."; 2089: runs "only when Claude Code is about to ask you for permission, or when it would otherwise auto-deny a call that can't prompt."
- hooks.md 2120: behavior "allow" grants the permission; deny and ask RULES are still evaluated. 2126: exit 2 without a decision leaves the flow unchanged.
- hooks.md 2096 + 737: input carries permission_mode; documented values include "plan".
- permission-modes.md 905 (critical-path removals, table includes plan): "In modes that ask, a PermissionRequest hook can answer the prompt."
- permissions.md 657-659 name the plan-mode limit only for PreToolUse "allow" and a mod's tool.check. Its heading ("Hook approvals in plan mode") and closing sentence ("To lift this limit on hook and mod approvals") are generic, so the vendor could extend the limit to PermissionRequest later.
- Changelog: the cached copy ends at 2.1.302. The live CHANGELOG.md (downloaded this session from raw.githubusercontent.com/anthropics/claude-code/main) was searched for 2.1.303-2.1.310: no PermissionRequest or plan-mode change except a Windows Git Bash fail-open fix (2.1.309). Cached-copy PermissionRequest lines (188, 189, 349, 378, 1080, 2008, 2661, 3236, 5500, 6175, 8191, 8240) say nothing about plan mode.
Field evidence (user report, not vendor docs; fetched this session):
- anthropics/claude-code issue 104446 (open, Claude Code 2.1.309, Linux): "A PermissionRequest hook answering allow does stop the prompt in plan mode, unlike a PreToolUse hook or a mod's tool.check", with the exact output shape this design uses.
Status: likely to work, not proven for Erez's client (Claude desktop app, which runs the hook alongside its own prompt card; hooks.md 2074 "whichever decides first applies"). The live test decides.

## Proposed change
1. New file ~/.claude/hooks/planmode-readonly-answer.js (Node). Header comment states its invariants: allow-only (never deny, never updatedInput or updatedPermissions), plan mode only, these 5 tools only, and that these tools must never gain a PreToolUse "ask" from another hook (it would answer that too). On stdin JSON it returns {"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}} ONLY when ALL hold:
   - hook_event_name === "PermissionRequest";
   - permission_mode === "plan";
   - tool_name is one of the 5 names (hard-coded set, second check behind the matcher);
   - tool_name is still a bare entry in ~/.claude/settings.json permissions.allow (read fresh each call; Erez removes a name there to restore the prompt).
   Otherwise, or on any error, it exits 0 with no output, so the normal prompt shows.
   Diagnostic trace, switched by a marker file: only while `<os temp dir>/planmode-answer-trace.on` exists, it appends one line {ts, tool_name, permission_mode, answered: true|false, reason} to `<os temp dir>/planmode-answer-trace.jsonl` (wrapped in try/catch; a trace failure never changes the decision). No marker = no file activity at all. The marker exists only during the live test.
2. Register under a NEW "PermissionRequest" key in ~/.claude/settings.json (none exists today), matcher = the 5 names joined by "|" (exact-match form, hooks.md 280), type command, command `node "C:/Users/Erez/.claude/hooks/planmode-readonly-answer.js"`, timeout 10, onFailure "continue" set explicitly (a failed hook = the normal prompt; hooks.md 784, 904). Applied through update-config.ps1 under /vet-code.
3. Tests before install: `node --check`; a test file feeding synthetic stdin: plan + each listed tool -> the allow JSON; default/auto mode, an unlisted tool, a name removed from a fixture settings file, bad JSON, missing fields -> no output; trace off -> no file written; trace on -> one line per call. Plus the /vet-code code reviews.
4. Live test, in Erez's real client after install: Erez opens a fresh session, switches it to plan mode, and sends a message Claude provides that asks for one call of each of the 5 tools (tabs_context_mcp without createIfEmpty). Claude creates the trace marker first and removes it after. Per tool, PASS = the transcript decision record shows source "hook" (not "user_temporary") and the trace shows answered:true. A sub-second flash of the prompt card is possible and is not a failure. Diagnosis of a FAIL: no trace line = hook not invoked (registration or matcher problem: fix and retest); trace line with answered:false = a guard mismatched (fix and retest); trace answered:true but a user prompt still recorded = Claude Code ignores the answer in this client (vendor limitation). A name that genuinely fails is removed from the matcher; if all genuinely fail, the registration and file are removed (one more gated change).
5. Recording the outcome and keeping watch:
   - The live-test result (per tool, with the diagnosis) is written to GEN-952 and to the GEN-58 log entry for this lesson.
   - If it passes, GEN-952 goes to Review with a one-time scheduled check about 3 weeks later that re-runs count-planmode-prompts.js for the 5 names and scans for any other allow-listed MCP tool that prompted in plan mode; its result goes into that run's report to Erez and onto GEN-952 (Done if 0 prompts and no new tools; otherwise a note and a follow-up).
   - The general lesson (read the vendor's docs and changelog before building on a platform behavior) is handled separately as a skill edit under review.

## Known residuals
- The hook cannot see WHY a prompt was raised. In plan mode, a PreToolUse "ask" from another hook on one of these 5 tools would also be answered. Today: three match-all PreToolUse hooks (auto-approve.js, confirm-send.js, notion-schema-guard.js) only allow/defer or ask for other tools; browser-site-gate.js returns early for tabs_context_mcp (browser-site-gate.js lines 82, 399) but asks on unparseable input or its own internal error (lines ~889, ~897). For a list-tabs read this is harmless.
- tabs_context_mcp with createIfEmpty:true creates an empty browser tab group: near-read-only, already allow-listed.
- Deny and ask permission rules still apply after the hook's allow (hooks.md 2120); settings.json has no deny rules and only two ask rules (*ApproveSizeUpTo*).
- A future Claude Code release could extend the plan-mode limit to PermissionRequest, or a server rename could stop the match; either way the hook goes inert and the old prompt returns (safe direction); the 3-week check catches it once.
