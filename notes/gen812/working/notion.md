Notion (MCP) gotchas — injected because this turn looks like Notion work. (The notion-duplicate-page safety note stays in the always-loaded global CLAUDE.md; the destructive-op incident classes below were moved here from it — see the "Destructive-op incident classes" section at the end.)

- Schema/reads are authoritative, not the page view. A page view omits properties with no value set, so a property's absence from one page isn't evidence it's missing — fetch the data-source schema before concluding a property doesn't exist. The converse also holds: don't assert a property/column EXISTS (or that there are duplicate columns) without checking the authoritative property list — the MCP editable-property list or a REST DB-schema read — and never attach invented supporting statistics to an unverified structural claim (GEN-543 wrap 2026-07-22: claimed two mirrored `Gain ratio`/`Gain Ratio` columns "0 conflicts across 177 tickets"; there is only one column and the stat was fabricated). Before designing around reading a database's rows/counts/aggregations, verify what a collection:// data-source fetch actually returns and which query tools exist — don't assume the rows come back in one cheap call. And a query result is evidence about its result set, never about the board: a REST `POST /v1/databases/<id>/query` filtered on an **optional** property (`Project`, `Assignee`, …) silently omits every row where that property is UNSET — which is how a duplicate of the very ticket being worked was missed in a "related tickets" sweep (2026-08-02, GEN-548 vs GEN-578: empty `Project`) — and a response carrying `has_more: true` means the read is incomplete, so exhaust `next_cursor` or scope the claim to what was actually read. For a board-wide sweep, filter on `Status` only (never on an optional field) and page to exhaustion before saying "nothing else."
- Before writing to or updating a page: don't assume a section is blank — a template or earlier edit may already hold that heading, so fetch current content first and fill the existing heading. For update_content, copy old_str verbatim from the fetch — the API escapes some characters (~ becomes \~), so a hand-built string silently no-ops. update_content ALSO silently no-ops when the target text spans multiple rich-text segments (e.g. it contains inline-code like `foo.jsonl` or `/wrap` — each code span is a separate segment), even with no special chars; the flattened match fails at the formatting boundary. When a page has inline-code in the target, don't fight update_content — replace the whole block by id via REST `PATCH /v1/blocks/{id}` with fresh rich_text (get the block id from GET /v1/blocks/{page}/children). (GEN-432 wrap, 2026-07-15.) When the edit CORRECTS a claim, first search the whole page for OTHER instances of that claim — one `old_str` fixes one occurrence and leaves the page self-contradicting (GEN-550, 2026-07-30: the "appender has no amend path" claim sat in two places; the first update fixed one and the ticket contradicted itself until a second pass). And re-read the changed region afterwards — the WHOLE containing paragraph plus its heading, read as a stranger would, not just the span you replaced: a replacement spliced into the middle can leave a dangling clause from the original text, or leave the neighbouring sentences still asserting what you just corrected (2026-08-03, GEN-607: a corrected "NOT installed" claim left the sentence before it demanding the install and the one after instructing an action already taken — three passes over one paragraph). Tick this check and the other-instances search off separately; performing the more interesting half feels like performing the bullet. When you rebuild a block's rich_text this way, pass every segment through as-is (minus the read-only `plain_text`/`href`) and edit only the one text segment you are changing — an array can contain `mention` segments (page links, users, dates) whose `text.content` is empty, so a loop that re-emits each segment as `type:'text'` silently destroys the link while the visible prose looks unchanged; verify afterwards that the segment types still include the mention (GEN-523 wrap, 2026-08-02.)
- **Notion page-text edits get a checker line** (`notion-write-verify.js`, GEN-453). Every SUCCESSFUL notion-update-page `update_content` / `insert_content` / `replace_content` call is followed by one line starting "Notion edit" (landed / CHECK / NOT verified / NOT done yet) — act on what it says; in a "landed" line, a changed block you did not intend (its "was ..." text lost) is a failure, not noise. **If a successful content edit gets no such line, the checker is not running: verify by hand via REST and say so.** It checks top-level block structure only; it does not replace re-reading the changed paragraph (bullet above). Not covered: REST/curl writes (including long GEN-58 write-ups appended via REST — re-read the "Current log volume" pointer first), notion-create-pages, content nested inside blocks, and a sub-agent's edits (its line goes to the sub-agent). An insert into a GEN-58 log volume older than the one the pointer names is refused (GEN-593). To test how Notion edits behave, use the practice page whose id is `NOTION_PRACTICE_PAGE_ID` in `~/.claude/hooks/auto-approve.js` — plain-text edits only; anything else aimed at it is refused.
- Writing a LONG block via REST: one rich_text segment is capped at **2000 characters** — a longer `text.content` fails validation (`content.length should be ≤ 2000`), which bites on GEN-58 full write-ups. Split the text across several segments inside ONE block (they render as continuous prose), not across several blocks. And to place a new block at a chosen position rather than at the end, `PATCH /v1/blocks/{parent}/children` accepts `after: <block-id>` alongside `children` — used to drop a new class-digest bullet directly under its class heading. (GEN-583, 2026-08-02.)
- Property value forms (notion-create-pages / notion-update-page): a single-page relation (e.g. Parent item) is a plain page-URL string, NOT JSON-quoted (the quoted form fails "Invalid agent URL: Failed to parse as URL"); a multi-relation takes a JSON-array string of page URLs (["url1","url2"]); a person/Assignee field takes a JSON-array of user-ID UUIDs (["userId"], not URLs). Don't over-apply the single-page rule to multi-value fields. (2026-10-08, Invoice Automation: a JSON-array string `"[\"<url>\"]"` for single-page `Parent item` on `notion-create-pages` saved correctly twice — GEN-801, GEN-802 — and `Status` select saved at create both times; so the array form is accepted, and the select-blank issue is intermittent — still re-fetch to confirm.) A **select** property (e.g. Team-Tasks `Status`) passed as a plain string at `notion-create-pages` time can silently NOT save (comes back blank) even when the option name is exact — set it after creation via REST `PATCH /v1/pages/{id}` with `{"properties":{"<Prop>":{"select":{"name":"<Option>"}}}}` and re-fetch to confirm (observed 2026-07-16 on two Team-Tasks creates; `Status` here is a `select`, not a Notion `status` type — the `status` form errors "expected to be select").
- **Resolve a mutation target's id from the target itself, and assert it in the call.** A page id lifted from a `notion-search` hit list, an earlier result set, or your own previous message is NOT evidence it is the ticket you mean — search returns many ids and they are indistinguishable by shape. Before any write, `GET /v1/pages/{id}` and check `properties.ID.unique_id.number` equals the GEN number you intend, and make the script ABORT on mismatch rather than proceeding. Verify-after-write catches this only once the damage is done (GEN-218, 2026-08-02: 10 blocks appended and Urgency/Priority changed on GEN-324 while intending GEN-218; the wrong id had already appeared twice in my own output as a link labelled GEN-218 and was read past both times).
- **A `GET /v1/blocks/{id}/children` read caps at 100 blocks** — `has_more`/`next_cursor` carry the rest. So a before/after block-count comparison across a write is meaningless on a page near or over 100 unless BOTH reads paginate to exhaustion: a 97-block page that gained 10 reads back as 100, looking like a delta of 3. Paginate, or verify the write by fetching the returned block ids directly. (GEN-583, 2026-08-02.)
- **Notion MERGES adjacent text segments that share annotations**, so a block you wrote as several sub-2000-char chunks reads back as ONE segment over the cap — and the read-modify-write round-trip then fails validation on a block you yourself created legally. Any edit to a long block must re-chunk the final text before sending, not just re-emit the segments it read. (GEN-583, 2026-08-02.)
- **Targeting a page in `notion-update-page`:** the `page_id` argument must be a **bare page UUID** (`39c6e495-d07c-81a4-…`), not the page URL — the URL form fails validation (`page_id should be a valid uuid`). Distinct from the relation-*value* rule above: a relation value is a page-*URL* string; the call's own target id is a *UUID*. (Verified live 2026-07-13, GEN-418.)
- Writing content: wrap any word.ext token (e.g. CLAUDE.md, sync.ps1) in backticks in both title and body — Notion auto-linkifies bare word.ext into a fake http:// link; inline code suppresses it. But inline code CANNOT hold a backtick, and Notion's markdown parser silently mangles a backtick-or-`$`-bearing span rather than erroring: writing the JS replace directives (dollar-ampersand, dollar-backtick, dollar-apostrophe, dollar-digit, dollar-dollar) as inline code produced stray backticks, stray `**`, and inserted backslashes, corrupting the very sequences the page was about (GEN-654, 2026-08-05). Put any sequence containing a backtick, or a `$` adjacent to one, in a FENCED code block instead — and re-read the rendered body afterwards, since nothing fails loudly.
- Relations & sub-items: relation filters can only target a concrete page (no dynamic "this page" self-reference), so a self-scoping per-page sub-items table isn't possible; to show a page's children, native Sub-items expand-arrows (driven by Parent item) self-scope in any view without a filter. A "This Page" chip may be a literal pointer to a page so named — confirm the real target, don't trust the label. Sub-items can be re-pointed to an existing relation via Sub-items > Advanced settings to consolidate a duplicate parent/child relation — verify the live settings before accepting any "can't be merged" claim.
- GEN-* IDs are Notion Team-Tasks pages, not Jira (Jira has no GEN project) — search the Team-Tasks database directly, not Jira.
- Notion REST API database id != MCP collection:// UUID: the ancestor-2-database URL in a notion-fetch response is the REST API database id (format xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx); the collection:// UUID in parent-data-source is a different identifier that does NOT work with POST /v1/databases/<id>/query. Always derive the REST id from ancestor-2-database, never from collection://.
- curl body to Notion REST in PowerShell: never pass the JSON body via inline -d '{"filter":...}' — PS 5.1 mangles embedded quotes passed to native exes. Write the body to a temp file and pass it via --data-binary "@$bodyFile".
- Attaching a code/text file to a page: `notion-create-attachment` rejects code extensions (`.js` fails as unsupported) — upload as `<name>.js.txt` and note the rename on the page; attach the returned `file-upload://` id to a page within one hour or the upload expires. To prove a code backup is byte-exact, round-trip it: `notion-download-attachment` with the `file_upload_id`, write the returned content to a scratch file (LF endings), and hash-compare against the original (verified byte-exact 2026-07-16, GEN-450).
- `notion-fetch` reads can be STALE — a PostToolUse hook (`notion-fetch-staleness.js`, GEN-377) usually warns you. `notion-fetch` serves reads from a lagging cache: the `as of <ISO>` line is the snapshot time, not live, and out-of-band edits (another session/client, the Notion UI, a REST write) aren't promptly reflected. The hook compares each read's `as of` against the page's live REST `last_edited_time` and injects a warning when the snapshot trails, so in the **main session** you'll normally be told a read is stale — heed it and re-read via REST before relying on the content. Caveats: it reads *page-level* `last_edited_time` (Notion bumps this on content edits per its documented behavior — verified here for top-level block writes, inferred for nested/UI edits), and it fails silent on any error (missing token, REST failure, connector-UUID rotation), so it's a backstop, not a guarantee. Two gaps it can't cover, on you: **(1) Sub-agents** — hooks do fire inside sub-agents, but this warning then lands in the sub-agent's context, not yours, and a sub-agent has no shell to do the REST re-read it calls for, so don't delegate time-sensitive Notion reconciliation (reading current log/ticket state you'll write to or decide from) to a sub-agent; do it in the main session. **(2)** It warns but doesn't block — for time-sensitive reconciliation, prefer reading via the Notion REST API directly (always live), or fetch the page fresh as the first read of the session. **(3) PROPERTIES go stale too, not just body content, and a stale property is more dangerous because you DERIVE from it:** 2026-08-02, GEN-557's first read of the session served a 3-day-old snapshot showing `Urgency: Not-urgent` when live was `Urgent`; the Priority derivation computed from it was wrong, and it was written into the ticket body where the next session would have trusted it. Re-read any property via REST before asserting it or deriving from it — and if you have already written a derived value somewhere, correct that too, not just your next sentence.
- A child-page mention in `notion-fetch` output DOES carry the target URL inline — it renders as `<page url="https://app.notion.com/p/...">Child Title</page>`. So "the page-mention link doesn't render an inline URL, can't resolve the child-page ID" is a false blocker: grep the fetched markdown (or the auto-saved tool-result file for an over-limit fetch) for `<page url=` and read the id from there — no need to open the Notion UI to copy it. (GEN-481, 2026-07-19: two GEN-58 write-ups were parked on the index body across two sessions on this false blocker; the Vol. 5 URL was present in the fetch the whole time.)
- Team-Tasks priority derivation (Gain ratio -> base priority; Urgent raises it). When drafting or materially updating a Team-Tasks ticket, set Gain ratio (1 = big gain for little effort / 2 = balanced / 3 = little gain for much effort) and Urgency (Urgent / Not-urgent), then set Priority: for Not-urgent, priority = base from Gain ratio -- Gain 1 -> High, Gain 2 -> Medium, Gain 3 -> Low; for Urgent, priority = Highest at Gain 1, else High (so any Urgent ticket is at least High, and Highest is reached only by Urgent + Gain 1). A Not-urgent ticket never exceeds High; Low is the floor (there is no "Lowest" option). When unsure, default to Not-urgent + Gain 2 -> Medium. Priority is a manual select (no Notion formula, to keep the coloured/groupable pill), so recompute it by this rule whenever Gain ratio or Urgency changes. A body append counts as a material update -- appending an "Also surfaced" recurrence via `insert_content` is a trigger to re-derive Gain ratio + Urgency (and recompute Priority) from the new content, not exempt because it's "only an append"; and a ticket still on a bare direct Priority with no Gain ratio / Urgency set gets both fields added at that point. (GEN-513, 2026-07-20; append-clause GEN-422, 2026-07-22; Urgency-rename + Urgent-raises model 2026-07-22.)

- Applying a ticket-gate-hashed Notion write (the `/vet-ticket` apply step): the `content`/`properties` sent via the MCP tool must match the hashed payload file BYTE-FOR-BYTE, or the gate blocks (`no usable ticket review record` — hash mismatch). Pass the LITERAL characters, read from the hashed file — a `\uXXXX` escape typed into an MCP string parameter is sent as literal backslash-u and changes the bytes (2026-09-29, GEN-757 filing: an em-dash written as a unicode escape blocked the write; resending the literal `—` matched).

## Destructive-op incident classes (moved from the always-loaded global CLAUDE.md, GEN-337)

Each is from a real damage event. Before the operation, snapshot at-risk adjacent state, perform it, then re-fetch and compare — surface unexpected deltas, not just whether the intended change landed.

- (a) For Notion select/multi-select schema changes (option-ID regeneration silently breaks view filters that reference them): snapshot views/filter rules + option IDs, re-fetch and compare.
- (b) Before dropping or merging a relation that was backfilled from another (e.g. consolidating Notion dual-relation pairs): a fill-only backfill's own "0 changes" / success condition does NOT prove the two columns agree — it skips already-populated rows, so a row re-parented after the backfill silently diverges. Audit for full row-by-row equality (source == target, catching empties AND mismatches), not the migration's success condition, before the drop.
- (c) Before writing a self-referential or inverse-of-parent Notion relation (e.g. `Related to Team-Tasks (Parent item)`, the inverse side of `Parent item` — writing it re-parents the listed pages rather than adding a see-also link, and may do so silently): snapshot the targets' current parent, write, then re-fetch and confirm the targets' resulting parent, not just that the value you set landed. **To parent a ticket, set the NEW ticket's own `Parent item` to the parent's URL — never write the inverse `Related to … (Parent item)` field to achieve parenting.** This holds identically at creation (`notion-create-pages`) and at later edits (`update_properties`): the wrong field re-parents the referenced page in both. (Team-Tasks has no generic 'related tickets' relation — cross-link tickets via body text.)

**Mechanism that protects each.** The `notion-schema-guard.js` PreToolUse hook forces a confirm-prompt at tool-call time for the mutations it matches: destructive column DDL (DROP/ALTER/RENAME COLUMN) and in_trash on notion-update-data-source (covers a, and b's drop), and a `(Parent item)`-suffixed relation write on BOTH notion-update-page (`update_properties`) AND notion-create-pages (a relation set at creation — the GEN-375 arm) (covers c). As of GEN-378 the hook ALSO gates raw REST/curl writes: a `Bash`/`PowerShell` mutating-HTTP call to `api.notion.com` (curl/Invoke-WebRequest + a write verb or body flag) is forced to `ask` — but only COARSELY (ask on ANY write), because a shell payload is opaque to the hook (the body may be a temp file it can't read), so it cannot tell which incident class a/b/c the write is; that judgment is on you at the prompt. So default to the MCP tools (`notion-update-page` / `notion-create-pages`) for routine writes — ticket status/body edits, block appends, GEN-58 log entries — which pass silently unless they match incident class a/b/c; reserve raw curl for reads (already exempt) and the rare write the MCP tools can't express, where you accept the prompt. MCP is the lower-prompt path, not a zero-prompt guarantee. Reads are exempt via an allow-list of Notion read endpoints (a POST path ending `/query`, or `/v1/search`). A matched call can never silently execute. This is live-verified for main-conversation calls; sub-agent-originated behavior is version-dependent and not yet live-verified (see GEN-337). Residual gaps NOT hook-matched — so covered only by this file's guidance, and only when it's in context: an obfuscated / variable-built REST-write URL that evades the regex (same accepted limitation as auto-approve.js's Atlassian arm), and any select/multi-select option-set edit not emitted as column DDL. Because this file is injected only on Notion-mentioning turns, open it yourself before any Notion mutation arising mid-turn.

- **/vet-ticket body writes -- the sent content must byte-match the hashed payload.** The gate re-hashes the ACTUAL `notion-update-page` tool_input at call time, so if you hash a payload file (Step 1 `--ticket-hash`) but then hand-type the `content` into the MCP call, any edge-whitespace drift changes the hash and the write blocks with `no-pass` -- a dropped trailing newline is the classic, and an extra top-level parameter added only at send time (e.g. `allow_async: false`) breaks it the same way, since the WHOLE tool_input is hashed (the reviewer PASS is bound to the old hash, so you must re-review after any content change). Make the hashed file and the sent string identical: trim leading/trailing newlines from the content BEFORE hashing so the hand-typed send form matches, or reproduce the edge bytes exactly. Diagnose a `no-pass` by hashing trimmed variants of the file and matching against the block event's `hash` in `ticket-gate-events.jsonl`. (2026-08-17, GEN-649 wrap.) Backslash sequences in the content (a quoted regex such as `\s{0,64}`, `\u{...}` escapes, Windows paths) also drift between the hashed file and the hand-typed call. Keep the content free of them (describe a regex, or point to its source line), then send the call once BEFORE review: it will block, and you check that the block event's `hash` equals the file's hash before spending a review. (2026-09-29, GEN-684 note: 3 hashes differed until backslashes were removed.)
- **A bare filename with a TLD-like extension in Notion page content is auto-linked as a URL**: `set-claude-key.ps1` was stored as a link to `http://set-claude-key.ps` followed by `1` (2026-10-04, GEN-765). Wrap every filename and path in backticks in Notion writes.
- **/vet-ticket reviewer sign-off can still arrive without its verdict block.** GEN-812's `reviewer-verdict-guard.js` bounces such hand-backs back to the reviewer, but it gives up after two bounces a turn and never sees plain-text delivery. Always run `--ticket-verify` before minting; on `no-token` after a report that reads as a finished review, follow /vet-ticket Step 7: ask the same reviewer to re-send its full report ending with the verdict block (token last) and re-verify -- no re-review or re-hash needed.
- **/vet-ticket: send the Notion call with exactly the keys you hashed.** The hash covers the whole `tool_input`, so an extra optional parameter (e.g. `allow_async: false`) added at apply time makes the call unmatched -- refused `no usable ticket review record`, pass left unconsumed. Either include it in the hashed JSON or omit it from the call (2026-10-11).
