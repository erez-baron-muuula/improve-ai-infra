# /wrap — end-of-session wrap-up

Run as the LAST actions of a session, after all other work is complete. Execute the steps in order. If any step fails, surface the failure immediately in the "📌 For you" block AND continue with the remaining steps that do not depend on the failed one; only stop a step that genuinely needs the failed step's output. Never silently skip a step or hide-retry.

**Report only what needs your eyes.** A step that ran and produced nothing actionable gets a checkmark in a one-line status roll-up, never any prose about it — not a sentence explaining what it didn't find, nor a line confirming it went fine (its ✓ is that confirmation). The report is the roll-up plus the detail block and nothing else: no preamble, no success recap, no closing narration about clean steps. The roll-up and detail block name steps in plain language ("Key check", "Unresolved items", "Config-health", "Auto-approval scan", "History + push", "Config sync"), never by step number. Surface a step's details only when it produced something to act on, decide, or verify: an unresolved-item ticket filed, a config-health candidate, an auto-approval entry added, a state-mutation failure or warning (git push, config sync — surfaced whenever the output shows a failure, a partial success, or any warning even with a success exit code (config sync's exit code stays 0 on a push warning — read the output, don't trust the code); a fully clean run is NOT restated in detail — it is carried by its roll-up ✓, which is itself the explicit success statement the standing exit-status rule requires), a newly-created file, or any failure/skip. A step that errored, was skipped, produced a warning, or could not determine whether it had anything to report never gets a plain checkmark — it gets an ✗ (failure), ⚠ (succeeded-with-warning), or "skipped" mark plus a one-line reason. Everything else collapses into the roll-up.

## Step 0 — Determine the active project
- Identify the active project from the working directory and from which project CLAUDE.md was read this session (projects are listed in the global CLAUDE.md Projects Directory table).
- If the session spans no project (global/cross-project work only), skip every project-specific step and run only the global steps: the config-health pass (global file), the auto-approval scan, and the global config sync.
- If the active project is genuinely ambiguous, ask Erez which project to wrap — one short question.
- If the active project has no documented "end session" closing steps (its SESSION HISTORY section, or equivalent), skip Step 6 and proceed.

## Step 0b — Key check (GEN-638)
Runs in every session — it is not project-gated, so Step 0's no-project skip does not apply to it — and BEFORE Step 1, so a found key becomes an unresolved item that Step 1 files in this same wrap.

Run the installed tripwire once, from the PowerShell tool, as a call of its own:
`& "C:\Users\Erez\.claude\scripts\key-leak-tripwire.ps1"`
It checks whether the value of any key Claude reads from this PC's own store (the `set-claude-key.ps1` key list in Credential Manager, plus Git's stored GitHub login) appears in any Claude session log on this PC written since its last clean check — including sessions that ended without `/wrap`. It prints one JSON object of key names, file paths, dates, counts and reason codes, never a value.

**Never open a file it reports as `found`** — not with Read, Grep, a shell command or a sub-agent, and not to "confirm" the finding: opening it copies the key into this session. This wins over any later step that would read this session's on-disk transcript (Step 1 and Step 4 after a `/compact`): if a `found` file is this session's own log (its name or folder is this session's `$CLAUDE_SESSION_ID`), compose those steps from the in-context summary instead, and say in the report that the transcript was not reopened because it holds a leaked key.

**Read the JSON whatever the exit code, and report every item in it**, so a found key never hides a problem from the same run:
- Each `checks` entry with `status` `found` → a line under a "Key check" sub-heading in the "📌 For you" block, in plain words: which key; where (the project folder and date of each listed file, plus the `moreFiles` count); and what to do — make a new key at the service that issued it, store it with `powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\.claude\scripts\set-claude-key.ps1" -Key <name>` in his own PowerShell window (for `github` / `github-login`: sign in to GitHub again through Git), cancel the old key, then have Claude run the check once with `-All` so the new key is checked against every log, not only recent ones. A found key is reported again at every wrap until it is replaced.
- Each found key is also an unresolved item for Step 1, filed through Step 1's own machinery (its unattended gate flow and duplicate checks): a To Do ticket titled `Rotate the <name> key — its value appeared in a session log`, assigned to Erez (only he can replace a key), under the AI-infra epic, its ID listed in Step 1's `Unresolved items filed` line like any other. An open ticket with that exact title is skipped (sub-step 5), and an open ticket that already tracks replacing that key takes the finding as an `Also surfaced` line instead (sub-step 6); either way the "📌 For you" line still appears.
- Any problem — a `checks` entry with `status` `could-not-check`, or any entry in `problems` → ⚠ in the roll-up, and one plain line per problem under the "Key check" sub-heading saying what was not checked (for `could-not-check`: that key was not checked at all). The next wrap re-checks the same logs automatically.
- `not-stored` and `too-short` are statuses, not problems: no line.
- Nothing found and no problem → ✓ only.

**The exit code is only a cross-check** (2 = a key found, 1 = could not complete, 0 = complete and nothing found). If the JSON cannot be read: exit 2 → ⚠ "a key was found but the details could not be read — run the check again before anything else"; exit 1 → ⚠ "the key check could not complete"; exit 0 → ⚠ "the key check's result could not be confirmed". If the call is refused or fails before the script runs → ⚠ with the reason. Never a ✓ without readable JSON.

**Traceability:** record each found key and each problem in the Step 4 HISTORY.md entry on its own line (`Key check: <name> found in <N> log(s)` / `Key check: could not check — <codes>`); when the wrap logs no project, the script's own state file already holds the record. Any found key or problem counts as "a note the steps require surfacing," forcing the full Step 7 report rather than the all-clean fast-path.

**Read-only** apart from the one line the script appends to its own per-PC state file (`~/.claude/hooks/key-tripwire-scans.jsonl`, never synced) — never edit or truncate that file.

## Step 1 — Capture unresolved items (all sessions)
Auto-file every unresolved item this session surfaced as its own Notion Team-Tasks ticket, for future discussion. Do NOT ask Erez to weigh in on, approve, or apply any of them during the wrap — file silently; the Step 7 report's past-tense list of what was filed is required and is not "discussing" them. This step runs in every session (it is not project-gated; a global-only session still runs it — it is not one of the project-specific steps Step 0 skips). It **overrides, for capture-only filing and for the on-demand ref-file appends in sub-step (3),** the standing rules "Before creating or materially changing a ticket in a tracker, draft the full proposal" and "On \"apply learnings\"" (their approval-before-filing gates) — it does **not** override approval for applying a learning to any other home (`CLAUDE.md`, a skill, a hook's code; those still need `/check` + Erez's approval in a future session), and it does not change the assignee logic in sub-step 7.

**Every Team-Tasks write this step and Step 3c make goes through the ticket-quality gate (GEN-508), UNATTENDED (GEN-702).** The gate hard-blocks every Team-Tasks create / duplicate / move / substantive-body edit unless a single-use pass minted by an independent review exists, so each write here — the create in sub-step 7 (and, if the GEN-145 symptom appears, its in-place body repair), the near-duplicate body append in sub-step 6, and Step 3c's create and append — is filed by running the `/vet-ticket` machinery: **reference that skill's flow, do not re-specify it here.** Per item, run it unattended: draft the payload — set `Urgency`/`Gain ratio`/`Priority` per `/vet-ticket` Step 1, which treats a create and a material body append alike (both are material, so both derive these fields) → get its `contentHash` per `/vet-ticket` Step 1 → spawn ONE independent `check-reviewer` against the ticket bar (`/vet-ticket` Step 2) → resolve any notes, then write the ticket-record (`/vet-ticket` Steps 3–4) → run the `/vet-ticket` Step 7 evidence precondition → mint the single-use ticket pass → issue the Notion write → re-fetch and confirm it landed (`/vet-ticket` Step 8). **No Erez-facing card:** Steps 1 and 3c carry the standing override exempting them from the draft-for-approval pause, so `/vet-ticket` Step 5's card is skipped and the mint proceeds silently; the Step 6 waive lane needs Erez and is therefore unavailable here. `check-reviewer` has no Notion tool, so the near-duplicate search is NOT its job on this lane — sub-steps 5–6 already did it before drafting; the reviewer judges only ticket quality against its bar.

**Bounded — an unattended filing must never loop or hang the wrap.** If the reviewer does not return a clean PASS, amend the drafted payload per its findings and re-review with a fresh `check-reviewer` (re-hashing first) — but cap this at **2 further review rounds** (count every round that does not end in a clean PASS, not only literal REVISE verdicts). If the cap is reached, OR the item is blocked on information only Erez holds, OR any step of the machinery hard-errors (a non-zero `--ticket-hash` exit, a mint or evidence-precondition failure, a post-mint apply failure such as `consume-failed` or a Notion API error, a sidecar/transcript read failure — illustrative, not exhaustive: any hard error stops it) → do NOT force-file and do NOT loop. Leave the item unfiled, surface it in the Step 7 report **with enough substance to act on later**, and record it durably so a gate-blocked capture is not lost — in the Step 4 HISTORY.md entry (per Step 4 sub-step 2) when this wrap logs a project, or, when the wrap logs no project so Step 4 is skipped (Step 0), in a dated recovery file `C:\Users\Erez\.claude\wrap-surfaced-not-filed-<timestamp>.md` whose path the Step 7 report then names (Step 1 runs in every session, so its durability is unconditional too) — for a later manual `/vet-ticket`. **A surfaced-not-filed item counts as a note the steps require surfacing**, so it forces the full Step 7 report (never the all-clean fast-path). (Same posture as sub-step 7's GEN-145 handling: once, do not loop.)

**Report what was filed and how the reviews went (interim early-warning — GEN-702).** For EACH item this step filed, the Step 7 report shows its reviewer outcome inline (e.g. `reviewer PASS, N review round(s)`), plus a one-line per-run tally: count filed; count that needed more than one review round before PASS; count surfaced-not-filed (per the bound above). Step 3c reports its own single filing the same way, in its own report line (Step 3c below). This is computed from this run's own observation of the filings it just made — no gate change, no persisted tag. It is an interim, after-the-fact visibility signal on this unattended lane, **not** the durable cross-session aggregate; that aggregate, and the per-caller `--source` tagging the gate's event log would need to produce it, are GEN-636. (`waived`/`declined` cannot occur on this lane — there is no card — so they are not counted.)

1. **Decide what's already resolved** (so it isn't re-filed): from the session itself, an item is resolved if you already applied it (a rule/skill/hook/file edit you made this session), already filed it as a ticket this session, or already resolved it with no open thread remaining. Judge this from the session — do not reconstruct it from the auto-approval log or git history. **After a `/compact`, the in-context summary is lossy and may omit what was applied or filed — source this from the on-disk transcript, not the compacted summary** (same as Step 4). The dedupe query in (5) is the durable backstop against re-filing something a *prior* session already captured.
2. **Identify unresolved items** — anything worth keeping that surfaced this session, is NOT resolved per (1), was NOT explicitly rejected by Erez, and is not a solution/feature/approach you VOLUNTEERED UNPROMPTED that Erez then didn't take up (he met it with silence or a topic change — a lapsed unprompted offer isn't an item he's carrying; this does NOT apply to a recommendation he ASKED you for, nor to anything he ENGAGED with, e.g. asked about or said "maybe later" — those stay fileable as deferred decisions/open questions; and when you genuinely can't tell whether his silence meant a lapse or a still-open thread, file it, per this step's default of never dropping on an uncertain call): behavioral learnings (candidate rule/skill/hook), technical findings / tech debt / bugs, follow-up action items, deferred decisions / open questions. **Among behavioral learnings, treat as a candidate every reversal Erez's pushback caused this session — everything GEN-58 (a) already flagged live, plus any his pushback caused that it didn't catch, whether he challenged a position and you reversed it or asked a probing question whose honest answer exposed a problem you should have caught in your own `/suggest`/`/check` pass before presenting (mere elaboration, or a question that adds genuinely new scope rather than testing what you already gave, does not count). Post-`/compact`, source these from the on-disk transcript per (1). For each, judge whether the flip reveals something about how you reason or work — deferring to his tone over a real argument, missing something self-review should have caught, or under-delivering a quality pass you implied was done. If it does, file it via (3)'s triage like any other behavioral learning. If not — the flip merely absorbed genuinely new information he supplied, or the gap a question exposed was minor, case-specific, and not a repeatable habit — do not file it, but record it in one line in the HISTORY.md entry ('Reversals judged non-learning: …') so the negative judgments stay reviewable. This is independent of GEN-58's immediate in-session log; a reversal may qualify for both.** **File generously:** include it unless it was already captured in a ticket this session, already resolved-and-closed with no open thread, or Erez rejected it. This excludes only the volunteered offer's content; a genuine behavioral learning the episode revealed (e.g. that you volunteer unrequested work) is still captured via (3). If none, this step is silent.

File NO ticket for it. Quote every append or merge verbatim (before/after for a merge) in the Step 7 report.
   - **Enforceable candidate** — could become a rule, a skill, a hook, or other system enforcement → continue to (4) and file a ticket as usual (applying it later still needs `/check` + Erez's approval).    If the session surfaced no learnings, the triage writes nothing and reports nothing — the step gets only its checkmark in the roll-up, like any other clean step.

## Step 3b — Signal-surface pending scan (GEN-501)
Read `C:\Users\Erez\.claude\hooks\signal-surface-pending.jsonl` (the GEN-501 detector's durable, crash-safe log). Each line is a JSON object `{kind:"detect"|"deliver"|"ack", session, prompt, file, ts, ...}` (`deliver` rows also carry `decision`; a retirement `ack`'s `reason` begins with a routing tag — see "Retiring a known-benign orphan" below). Reconcile by `session`+`prompt`: a `detect` with a matching `deliver` was handled at that turn's Stop — the pairing itself needs no report (the `deliver`'s `decision` field records what happened: nudged, cleared as surfacing-designed, suppressed with the exposure recorded, or consumed on a hook-continuation turn — that last kind gets its own reporting, below). A `detect` is also closed by a matching `ack`, which retires it as a known-benign orphan (see "Retiring a known-benign orphan" below); an `ack` matches on `session`+`prompt`+`file`, NOT on `session`+`prompt` alone, because one turn can leave several `detect` lines for different files and an `ack` is a permanent judgment about one named mechanism. An **unpaired `detect`** (no matching `deliver`, no matching `ack`) means a turn built a signal-producing mechanism but no `deliver` was ever paired to it — either the session died before its Stop hook ran, or the Stop ran normally but a marker-unlink failure aborted the pairing (GEN-679) — leaving the `detect` permanently unpaired — the exact "signal that never reaches Erez" case the enforcer exists to catch, surfaced here as the fallback. For each unpaired `detect`, add a line to the "📌 For you" block under a "Signal-surface (unsurfaced)" sub-heading naming the file and turn, so Erez can check whether that mechanism ever got a surfacing path. Also reconcile the `deliver` rows with `decision:"skipped-continuation"` (GEN-679 — written when a mechanism is built on a hook-continuation turn, where the nudge is structurally forbidden). Report such a row ONLY if it is not already accounted for. A row is accounted for if EITHER: (a) another `deliver` row with the same `session`+`prompt`+`file` carries a judged decision (`nudge`, `cleared-surfacing-designed`, or `suppressed-block-out`) — the mechanism was already judged on the main turn and this continuation row is just the nudge→fix compliance cycle re-tripping the detector, so treat it as handled and do not report it (this is the mechanically-available discriminator; matching on `session`+`prompt`+`file` cannot distinguish a genuinely new same-file mechanism from the compliance cycle — an accepted trade-off — and a compliance fix that instead lands in a different file simply won't match and is safely over-reported); OR (b) it is closed by a matching `ack` (matched on `session`+`prompt`+`file`). A row that survives both tests normally means a real signal-producing mechanism was built on a continuation turn and got no surfacing judgment — rarely, it is a main-turn leftover marker consumed by a sibling-spawned continuation (the hook header's documented mislabeling residual). Either way it needs the same human look as an orphan: list it under the same "Signal-surface (unsurfaced)" sub-heading naming the file and turn, and retire it per "Retiring a known-benign orphan" below. When matching or copying `file`, note it may be a sentinel — `(unknown)` or `(content-match)` — rather than a path; copy it verbatim. When the row's `file` is `(unknown)`, additionally list the `file` values of every `detect` row sharing its `session`+`prompt` as candidate names to help the human look — but the retiring `ack` still copies `(unknown)` verbatim from the `deliver` row (copying it is what closes the row; the recovered candidates are for the human, not the `ack`). The aggregate 90-day FYIs that tally these retirements by cause are defined together below. If every `detect` is paired and no `skipped-continuation` row remains to report (per the accounting above) — the common case — this step gets only its checkmark — no "nothing pending" line. Also raise the aggregate 90-day FYIs from the retirement `ack` lines, routed by cause — for each, count the matching `ack` lines whose `ts` falls within the last 90 days and, at **two or more**, add a one-line FYI naming that count; below two, say nothing. (1) **Detector-retune** — `ack` lines tagged `false-detect:` (the detector fired but no signal-producing mechanism was built), since a detector that repeatedly fires on nothing is over-firing and its patterns want retuning (that retune is GEN-510's job, not `/wrap`'s). (2) **Continuation coverage-gap** — `ack` lines tagged `surfaced-elsewhere:` that close a `skipped-continuation` row, since real builds recurring on continuation turns predominantly mean the enforcer has a systematic coverage gap there (a design-revisit signal, not a detector retune). (3) **Orphaned-detect reliability** — `ack` lines tagged `surfaced-elsewhere:` that close an unpaired `detect` orphan, since a recurring need to hand-retire benign orphans means detects are repeatedly ending up unpaired. The count cannot tell WHY (per the hedge above, either the session died before Stop, or the Stop ran but its marker-unlink failed — the GEN-679 bug class), so a rising count is a prompt to read the acks and surrounding log evidence and decide between routine session death and a recurring pairing bug — not a claim that pairing is broken. Individual retirements would otherwise hide the trend. Every **tagged** retirement `ack` feeds exactly one of these three, by its tag and the row kind it closes. **Report-only — never mutate, rewrite, or truncate the log here** (acting on an orphaned detect is a normal follow-up, not a `/wrap` action). The log is append-only and left to grow, exactly as its sibling durable logs (`credential-denials.jsonl`, `deferred-calls.jsonl`) already are — each line is a few hundred bytes and a signal-building turn is infrequent, so growth is negligible; if it is ever actually observed to be a problem, add bounding to the detector itself then (do NOT rewrite the log from `/wrap` — a concurrent hook append during an unlocked rewrite could silently drop an unpaired detect, the precise loss this log exists to prevent, the GEN-218 hazard class). If the file is missing or empty, the step is a clean checkmark.

**Retiring a known-benign orphan.** An unpaired `detect` — left either by a session that died before Stop or by a normally-completed Stop whose marker-unlink failed (GEN-679) — and, since GEN-679, an un-acked `skipped-continuation` `deliver` row (a completed Stop where nudging was structurally forbidden) — are permanent, so a confirmed false alarm would otherwise re-surface at every future `/wrap`.   - **exit 1** (lock not acquired within its ~180s budget), **exit 3** (the appender could not safely write the target — either its structure was not recognized, or an internal/write failure hit after the lock was taken; its message says which), or **a second exit 4** (the text you reshaped was still malformed — or a FIRST exit 4 that arrived with no visible message): the appender has already written the composed entry to a `HISTORY.pending-<sessionid>-<timestamp>.md` recovery file next to the target — the text is safe there. EXCEPTION: if the appender printed `RECOVERY FILE NOT WRITTEN`, that file does NOT exist and the sub-step-1 temp file is the only surviving copy — name that instead.
  - **exit 2** (bad arguments — missing/misnamed `-Path` or `-EntryFile`, empty entry file, or empty `-TocLine`): the appender writes **no** recovery file for these. The entry survives only in the sub-step-1 temp file — keep it, and report its path.
  Surface it in Step 7 stating the exit code, the surviving-copy path (the recovery file for 1, 3, or a second 4 — or the temp file if `RECOVERY FILE NOT WRITTEN` was printed; the temp file for 2), and that `/compact` requires the explicit break-glass `C:\Users\Erez\.claude\.skip-loggate`. ## Step 4b — Git commit + push
Runs only after a successful Step 4 appender write (skipped on a BLOCKED wrap, and when the project is not a git repo).
- **Stage only the exact files this wrap-up touched** — list them explicitly to `git add` (HISTORY.md plus any config/rule/code files you actually changed this session). Do NOT `git add -A` / `git add .`: with concurrent sessions sharing one working directory that can sweep another session's in-progress files into this commit (GEN-218 Part 3).
- Commit on the current branch (no separate branch / PR).
- **Push, then integrate only if the push is refused as out-of-date (concurrent-session hygiene).** `git push`. If it succeeds this step is done — no rebase, and uncommitted work anywhere in the tree is irrelevant. That is the common case, and attempting it first keeps the frequent path to one command with nothing to parse. If it fails, read WHY before acting: only a **non-fast-forward / fetch-first rejection** — git reporting that the remote holds work this clone does not have — means the remote has advanced and integration is needed. Any OTHER push failure (auth, network, a protected branch, a declined pre-receive hook) is not a concurrency problem: stop there and surface it in Step 7 as its own error, naming the actual cause, and do NOT enter the branches below — they would report a credentials or branch-policy failure as another session blocking you. On a genuine out-of-date rejection, run `git status --porcelain` and choose by what is actually in the way:
  - **Tree clean** → `git pull --rebase origin <branch>`, then `git push`.
  - **Every dirty path belongs to THIS session** — a file this session created or modified, whether or not this wrap's commit included it (a scratch or generated artifact left untracked is the common case) → `git stash push -u -m "wrap-$CLAUDE_SESSION_ID" -- <those exact paths>`, rebase, push, then restore by that exact name: `git stash list`, find the entry carrying that message, and `git stash pop stash@{<its index>}`. **Never a bare `git stash pop`** — the stash stack is shared by every session in this working tree, so a bare pop can apply a sibling's entry into your tree. Confirm the pop's exit status; on a pop conflict STOP LOUD and name the stash entry so the work is findable. Restore any stash you took before this step is finished, on EVERY exit path — switching branches below does not cancel that obligation.
  - **ANY dirty path belongs to another session** → STOP LOUD, tree untouched: another session's uncommitted work is not yours to stash, commit, or revert. The commit is already made and un-pushed, so nothing is lost. Surface in Step 7 the paths involved and both recovery routes — push by hand later, or re-run `/wrap`, noting that a re-run replaces this session's HISTORY.md entry only while THIS session is still open (Step 4's reconcile matches this session's own marker); a re-run from a new session PREPENDS a second entry for the same work.
  - If the push after integrating is ALSO rejected as out-of-date (a sibling pushed again in between), re-run the integrate-then-push at most ONCE more; if it is rejected out-of-date a third time, STOP LOUD and surface it in Step 7 rather than retrying again, naming any stash still outstanding.
  Do NOT use `git pull --rebase --autostash` or the `rebase.autoStash` config anywhere here: they stash whatever is dirty in the shared working tree, a sibling session's files included, which is the one thing this step must not do. And do not run `git pull --rebase` before knowing the tree is clean or has been made clean — in a shared working tree it is refused outright ("cannot pull with rebase: You have unstaged changes") whenever any session has uncommitted work, which is the normal condition here, not an edge case (GEN-218).
- **If `git pull --rebase` fails once attempted,** distinguish the cause before acting: a real merge conflict leaves a rebase in progress (`.git/rebase-merge` or `.git/rebase-apply` exists) — run `git rebase --abort` and STOP LOUD (local commit intact and un-pushed; surface it in Step 7 for Erez to reconcile and re-push), and if a stash from the branch above is still outstanding, name it in that report so the work is not thought lost. Any other failure that started no rebase (network or auth during the pull's own fetch, a stale index lock, no disk space) needs no abort — surface it as its own error in Step 7 and stop; do NOT mislabel it a conflict. Verify the final push's exit status explicitly per the standing state-mutation rule; a warning-but-success still counts as pushed.
